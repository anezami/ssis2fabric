### 2026-05-26T18:15:00+02:00 — Phase 7–10: end-to-end deploy of both flavors

- **Phase 7 (land data).** Regenerated 5 parquet files in `out/raw/` via `out\raw\_csv_to_parquet.py`. Two fixes were needed: (1) `Products.IsActive` ships in the CSV as `True`/`False` strings, not 0/1 — added a map step before write; (2) pandas/pyarrow default to nanosecond Parquet timestamps which Fabric Spark **rejects** with `Illegal Parquet type: INT64 (TIMESTAMP(NANOS,false))` — added `coerce_timestamps='us', allow_truncated_timestamps=True` to `to_parquet`.
- **OneLake upload via MCP didn't work for binary parquet.** `fabric-onelake_upload_file` and `fabric-onelake_create_directory` both returned HTTP 400 against `lh_ssis_demo.Lakehouse`. Fell back to the OneLake DFS REST API (PUT `?resource=file` → PATCH `?action=append&position=0` → PATCH `?action=flush&position=<len>`) with an AAD token for `https://storage.azure.com/`. That worked first time and auto-created `Files/raw/`. `fabric-onelake_list_files` and `fabric-onelake_list_tables` MCP calls worked fine for verification.
- **Phase 8 (Flavor A — Warehouse).** Dylan's `migration\warehouse\deploy.ps1` deployed `00_schemas.sql` → `04_load_orchestrator.sql` cleanly via `Invoke-Sqlcmd` + AAD token for `https://database.windows.net/`. No T-SQL edits needed — Dylan already used VARCHAR (no NVARCHAR), no IDENTITY, surrogate keys via `ROW_NUMBER()`, no `DEFAULT NEWID()`. **`COPY INTO` from OneLake fails** under sqlcmd-passed Entra tokens: `Msg 13840 — Access token couldn't be fetched for storage path '...'`. The warehouse can't OBO-exchange the caller's database.windows.net token for OneLake. Tried both `.dfs.fabric.microsoft.com` and `.blob.fabric.microsoft.com`; `CREDENTIAL = (IDENTITY = 'External User identity')` was a syntax error (that identity is Synapse-only, not Fabric). Workaround: wrote `migration\warehouse\_load_via_insert.py` to bulk-load `stg.*` via pyodbc with the AAD token attached as `SQL_COPT_SS_ACCESS_TOKEN=1256`, using multi-row `INSERT VALUES` (200 rows per statement). pyodbc `fast_executemany` is **too slow on Fabric Warehouse** — 6,000 rows takes >40 min row-by-row vs ~1 min with 30 batched multi-row inserts. After load, `EXEC dw.usp_RunAll` produced the expected `500 / 100 / 2000` for DimCustomer/DimProduct/FactOrders. Saved to `out\baseline\warehouse-rowcounts.json`.
- **Phase 9 (Flavor B — Lakehouse + notebook).** Created notebook `nb_ssis_demo_migration` (id `7d805094-17be-46b1-949d-aa710324f393`) via Fabric REST `POST /v1/workspaces/{wid}/items` with the .ipynb base64-encoded as `definition.parts[0].payload`, `payloadType=InlineBase64`. Updated `metadata.dependencies.lakehouse.default_lakehouse` in the .ipynb to bind the notebook to `lh_ssis_demo` before upload. The MCP `fabric-core_create-item` couldn't take an inline notebook body — REST was the right path. Item create returns 202 with `Location` for the LRO; polled until `Succeeded` then fetched the item ID by listing workspace items by displayName (the LRO response body itself didn't carry the id reliably in PowerShell). For re-uploads, `POST /v1/workspaces/{wid}/items/{nbId}/updateDefinition` works the same way. Notebook run: `POST /v1/workspaces/{wid}/items/{nbId}/jobs/instances?jobType=RunNotebook` → poll the instance.
- **Notebook debugging is opaque.** Failed notebook runs report a single error code `System_Cancelled_Session_Statements_Failed` with no cell stdout in the REST monitoring API. To isolate the real Python traceback I built a diagnostic notebook that wrapped each migration step in try/except and persisted `traceback.format_exc()` to `Files/diag_log_dir/` via `spark.sparkContext.parallelize([log], 1).saveAsTextFile(...)`, then downloaded the part-00000 file via the DFS REST API. That's how I found the nanosecond-timestamp issue mentioned above. Other notebook gotchas: (a) **SparkSQL string literals must be single-quoted** — double quotes are treated as identifiers under the default config and break `CASE WHEN ... THEN "LOW" ...`; (b) `saveAsTable("foo")` without `.option("path", abfss://...)` is unreliable when the default lakehouse binding isn't fully wired; (c) abfss paths with friendly workspace/item names work but IDs are safer (`abfss://<wsid>@onelake.dfs.fabric.microsoft.com/<lhid>/...`).
