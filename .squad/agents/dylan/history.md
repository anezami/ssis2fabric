#### DTSX gotchas hit (write these on the wall for next time)

1. **Console encoding on Windows.** ssis-analyzer prints a Unicode right-arrow (`\u2192`) in path output. The default Windows `cp1252` console can't encode it → `UnicodeEncodeError`. Workaround: `$env:PYTHONIOENCODING = "utf-8"` before running, or always pass `--json`. The package itself parses fine — the crash is downstream.
2. **Script Component `componentClassID` must be a GUID** (`{2E42D45B-F83C-400F-8D77-61DDE6A7DF29}` or `{0617AA7D-4176-4AF0-8684-96BCAF85B36F}`), not a short-name like `Microsoft.ScriptComponentHost`. The short-name map in `lookups.py` does NOT include the script component — class resolution falls back to "unknown" and `_extract_script_component` is never called.
3. **C# source must live in a `SourceCode` array property**, not in some `<ScriptComponentProject>` child. Format:
   ```xml
   <property name="SourceCode" isArray="true" state="escaped">
     <arrayElements>
       <arrayElement>\main.cs</arrayElement>
       <arrayElement>using System; ...</arrayElement>
     </arrayElements>
   </property>
   ```
   Alternating filename/content pairs. With `state="escaped"`, HTML entities (`&lt;`, `&gt;`, `&amp;`) inside the code get unescaped after parsing — so write `if (price &lt; 50m)` in the XML to get `if (price < 50m)` in the extracted script.
4. **`PackageFormatVersion`** must be on the root as both an attribute (`DTS:PackageFormatVersion="8"`) AND a child `<DTS:Property DTS:Name="PackageFormatVersion">8</DTS:Property>` — the analyzer's `get_format_version` tries the attribute first but other tooling reads the child.
5. **`dataType="System.Int32"` on a string property** silently works in the analyzer but is wrong — use `System.String` (cost me nothing here but will trip up downstream consumers).
6. **Flat File column delimiters** in format 8: literal CR/LF inside attribute values needs to be `_x000D__x000A_` (the SSIS-flavored escape). Last column in the row uses the row delimiter, others use the column delimiter (`,`).
7. **Lookup component cache mode**: `CacheType=1` = Full Cache (default, loads reference table once). `NoMatchBehavior=1` = Send rows with no match to no-match output (vs failing).
8. **OLE DB Destination `AccessMode=3`** = Table or view — fast load. `OpenRowset` = `[schema].[table]`.
9. **`<DTS:Variables/>`** can be self-closed if empty. Same for `<DTS:Executables>` but obviously not in our case.

### 2026-05-26 — Phase 1+2+3 execution (VM run + .ispac/.bacpac + specs)

Did the full end-to-end pass against the live VM (`20.163.102.57`). Working code/notes in `migration/MIGRATION.md`. Highlights:

#### Connection & data loading
- `Invoke-Sqlcmd` from dev box → VM works fine: `sa` over TCP 1433 with `-TrustServerCertificate`. NSG already allows our caller IP. Always read the password fresh from `infra/.secrets/sql-admin.json` — never log it.
- All three SQL setup scripts (`ssis/sql/00..02`) are idempotent and run cleanly. Source row counts captured to `out/baseline/source-rowcounts.json` (20/500/100/2000/6000).

#### File transfer to VM — `az vm run-command` + inline base64
- The auth path that works in this env is `az vm run-command invoke --command-id RunPowerShellScript --scripts "@local-file.ps1"`. The script file can be ~50KB+ — plenty for inlining base64 of multiple ~10KB DTSX files in one round-trip.
- Pattern: read each file → `[Convert]::ToBase64String([IO.File]::ReadAllBytes(...))` → bake into a here-string PS template → write out → invoke. Verified by listing the resulting files and matching `Length`.

#### dtexec on hand-authored DTSX — **runtime validation gaps** (the big finding)
The DTSX I authored last session parse cleanly through `ssis-analyzer` but **fail `dtexec` runtime validation** for three distinct reasons:

1. **OLE DB Source w/ `AccessMode=2` (SqlCommand) still needs an empty `OpenRowset` property** in the XML. dtexec's error: `0xC0207001 ... missing required property "OpenRowset"`. The analyzer never reads this because it switches on AccessMode itself. Lesson: when hand-authoring, set BOTH `OpenRowset=""` and `SqlCommand="..."` regardless of AccessMode.
2. **Flat File Source needs `FileNameColumnName=""`** as an explicit property. Same shape — dtexec validates property presence, analyzer doesn't.
3. **Script Component requires a precompiled binary** baked into the DTSX as a base64 BLOB inside the `BinaryCode` property. Pure XML source code (the `SourceCode` array I produced) is necessary but not sufficient. SSDT compiles the C# at design time and embeds the assembly. There is no documented way to do this purely from XML. Result: dtexec fails with `0x80070005 Access is denied` and (separately) the SourceCode array property triggers `0xC020F44C arrayElementCount not found` because dtexec wants an explicit count attribute on the `<property isArray="true">` element.

**Pragmatic workaround:** populate `SalesDW` via T-SQL equivalents that exactly mirror each package's semantics. Documented in `migration/MIGRATION.md`. Target counts (500/100/2000) match the source-side expectations so Helly still has a valid truth baseline.

**Future work to make dtexec actually run these DTSX:**
- Add `OpenRowset=""`, `OpenRowsetVariable=""`, `SqlCommandVariable=""`, `ParameterMapping=""`, `DefaultCodePage="1252"`, `AlwaysUseDefaultCodePage="false"` to OLE DB Sources & Lookup ref tables.
- Add `FileNameColumnName=""`, `RetainNulls="false"` (already set) to the Flat File Source.
- Replace `SCR_Enrich` Script Component with two `Derived Column` transforms (`UPPER(Sku)` + `MarginCategory` from `Price`). Avoids the SSDT binary requirement entirely.
- For the `SourceCode` array property: add `arrayElementCount="2"` attribute. (Still doesn't solve the binary issue — only relevant if you keep the Script Component.)

#### `.ispac` build without SSDT
- Confirmed an `.ispac` is just a ZIP (Open Packaging Convention). Built one in PS via `[System.IO.Compression.ZipFile]::CreateFromDirectory(...)` — `Compress-Archive` is brittle with `[Content_Types].xml` (square brackets confuse the wildcard expander; use `-LiteralPath` for `Set-Content`).
- Minimal manifest needs an `<SSIS:Packages>` list with `<SSIS:Package SSIS:Name="..." SSIS:EntryPoint="True"/>` entries; `[Content_Types].xml` declares the file extensions. That's enough for the analyzer pipeline and the spec-writer.

#### `.bacpac` export — install sqlpackage locally, export over TCP
- `microsoft.sqlpackage` is published as a **.NET global tool** (`dotnet tool install -g microsoft.sqlpackage`, v170.x). Way faster than installing it on the VM via `winget`/MSI and means we can call it from the dev box.
- Export ran over TCP/1433 directly to the VM (`/SourceTrustServerCertificate:True /SourceEncryptConnection:True`) — ~70s per DB. No need to round-trip the bacpac off the VM.

#### Tools-of-the-trade notes
- `az vm run-command invoke` truncates its JSON stdout response at ~10KB. If you have a long log to capture, write it to a file on the VM and either Tee or do a follow-up invoke to read it back.
- `Invoke-Sqlcmd` is happy to take heredoc-style multi-batch T-SQL via `-Query` — no need to drop each batch in a temp file.
- When base64'ing for `--scripts @file.ps1`, mind PowerShell here-string interpolation: prefix any literal `$` with backtick (`` `$ ``) or use single-quoted here-strings.
